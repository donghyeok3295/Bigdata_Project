## 1. 원칙

1. **main은 언제나 실행 가능한 상태**로 유지한다.
2. **숫자는 코드 실행 결과에서만** 가져온다. 논문·발표 수치는 `results/` 파일에 근거가 있어야 한다.
3. **규칙을 바꾸면 문서부터** 고친다: 명세서 수정 → `DECISIONS.md` 기록 → 코드.
4. **막히면 24시간 안에 공유**한다.
5. **주장은 결과가 허용하는 만큼만** 한다. "최적", "입증", "구급차 수" 같은 표현을 쓰지 않는다.

## 6. GitHub

### 6.1 브랜치

```
main   ← 매주 금요일 dev에서 병합 (실행 가능 상태만)
 └ dev ← 기능 PR이 모이는 곳
    ├ feat/{역할}-{주제}   예: feat/A-center-activity
    ├ exp/{역할}-{주제}    예: exp/B-g2-dplus
    └ fix/{역할}-{주제}
```

`main`, `dev`는 보호 브랜치: PR + CI 통과 + 리뷰 1인.

### 6.2 커밋 메시지

`type(scope): 내용` — `feat`, `fix`, `data`, `exp`, `test`, `docs`, `ci`, `chore`

예: `feat(pipeline): 전체 기록 기준 센터 출동 활동량 계산`

### 6.3 PR 템플릿

```markdown
## 무엇을
## 왜 (이슈 #, 요구사항 ID)
## 검증 (테스트, 행 수·지표 변화)
## 문서 변경 필요 여부
```

변경 400줄 이하 권장, 노트북은 출력 제거 후 커밋.

## 7. 데이터 관리

- 원본·중간 데이터, 실제 샘플은 **저장소에 올리지 않는다** (`data/`, `models/`는 `.gitignore`).
- **데이터를 한 줄 열기 전에 이용약관부터 확인한다.** "구매 후 30일"이 다운로드 기한인지 이용 기한인지, 팀 공유·CI 사용이 허용되는지 확인해 `docs/data_terms.md`에 기록한다(D-006). 실시간 API의 호출 제한·이용 조건도 같은 문서에 적는다.
- 구급 원본은 받은 날 팀 드라이브 `raw/ems/`에 보관한다.
- CI와 테스트는 **합성 샘플**(`tests/fixtures/synthetic_10k.parquet`, 실제 분포를 흉내 낸 가짜 데이터)을 쓴다.
- 드라이브 구조: `raw/ems/`, `raw/asos/`, `raw/speed/`, `raw/parking/`, `ref/`, `live/`(실시간 수집)
- 실시간 수집 데이터는 시스템 입력·스트림 실험용이다. **모델 학습 데이터 크기로 소개하지 않는다.**

## 8. 실험 관리

- 모든 실험은 `configs/models/*.yaml`로 설정한다.
- 실행마다 `docs/EXPERIMENTS.md`에 한 줄 기록: `날짜 | run_id | 모델 | D+/D− | Brier | log loss | calib slope | AUC | 비고 | 담당`
- 모델마다 **같은 탐색 공간·같은 시행 횟수**로 튜닝한다. 한 모델의 설정을 다른 모델에 돌려쓰지 않는다.
- **시험 구간(2025)은 8주차 최종 평가에서 한 번만** 연다. 그 전에 전처리·피처·보정·임계값을 모두 동결하고, 동결 커밋을 태그(`freeze-v1`)로 남긴다.
- 결과표는 스크립트가 만든 CSV를 그대로 쓴다.
