## 1부. 우리 프로젝트는 무엇인가

### 1.1 한 문장

> 서울에서 119 구급 신고가 들어왔을 때, **"이 안전센터가 출동하면 8분 안에 도착할 확률"**을 과거 출동 기록으로 학습한 모델이 계산하고, 주변 센터끼리 비교해 보여 준다.

### 1.2 왜 하나 (문제)

- 구급차는 신고부터 현장 도착까지 8분 안에 도착하는 것을 목표 기준으로 본다. 그런데 서울 2024년 기록에서 **8분을 넘긴 출동이 47.9%**다. 절반 가까이가 기준을 넘는다.
- 늦어지는 이유는 거리만이 아니다. EDA를 해 보니 같은 거리라도 시간대, 관할 밖 출동(관외출동), 비, 교통 정체, 그 시간에 신고가 몰렸는지에 따라 8분 초과율이 달라진다.
- 지금 화면에 보이는 정보(가까운 센터)만으로는 이런 조건이 반영된 "늦을 가능성"을 알 수 없다. 그래서 신고 시점에 알 수 있는 정보로 **확률**을 계산해 보려는 것이다.

### 1.3 무엇을 만드나 (최종 목표, 12월 기말)

| 구분 | 최종 목표 | 지금(11.02) |
| --- | --- | --- |
| 연구 | 기본 정보로 만든 기준 모델(G0)에 **강수, 구·센터 활동량, 교통 정체**를 하나씩 더했을 때 예측이 얼마나 좋아지는지 실제로 실험한 소논문 | 기준 모델 G0 1차 학습·보정·평가 완료(예비) |
| 시스템 | 신고 위치를 넣으면 주변 안전센터 5곳의 8분 내 도착 확률을 비교하는 웹 화면. 실시간 교통·기상을 받아 모델이 계산 | 화면 목업 완료(수치는 가상 값). 모델 연동 전 |
| 빅데이터 처리 | HDFS 저장 → Spark 정제 → 피처 결합 → 학습 → 서비스까지 이어지는 파이프라인, 실시간 수집·스트리밍, Docker·CI·Kubernetes 배포 | HDFS 적재·Spark 정제 완료. 수집·스트리밍·배포는 설계 단계 |

- **연구용 참고 정보**다. 실제 출동 지령이나 배차에 쓰지 않는다. 슬라이드에도 이 문구를 넣는다.
- "원인 분석"이 아니라 **예측**이다. "비가 오면 늦어진다(인과)"가 아니라 "강수 정보를 넣으면 8분 초과를 더 잘 맞히는가(예측가치)"를 묻는다.

### 1.4 연구 질문

| 질문 | 내용 | 비교 방법 |
| --- | --- | --- |
| Q0 (기준) | 구급 기록(시간, 지역, 센터, 관외출동, 거리)만으로 8분 초과를 얼마나 맞히고, 확률은 믿을 만한가 | 기준 모델 G0 |
| Q1 (RQ1-a, b) | 신고 직전 60분 동안 **구에 신고가 몰린 정도**, **출동 센터가 바빴던 정도**를 더하면 얼마나 달라지나 | G0 대비 Brier·log loss 변화 |
| Q2 (RQ2) | 신고 직전 시간의 **교통 정체 지수**를 더하면 얼마나 달라지나 (강수도 같은 방식) | G0 대비 변화 |

### 1.5 용어 (발표 전에 팀원 모두 같은 뜻으로 쓰기)

| 용어 | 뜻 |
| --- | --- |
| 8분 초과 (`y_late`) | 신고 접수 시각부터 현장 도착 시각까지 8분을 넘으면 1, 아니면 0. 모델이 예측하는 대상(라벨) |
| 원본 / 코호트 | 원본은 서울 출동 기록 전체(정제 전). 코호트는 라벨을 믿을 수 있는 기록만 남긴 것(정제 후) |
| 안전센터 코호트 | 코호트 중 **안전센터** 출동만. 모델은 이것으로 학습한다(현장대응단·구조대 제외) |
| 관외출동 | 신고가 들어온 구와 출동한 센터의 소속 구가 다른 출동 |
| 활동량 | 신고 직전 60분 동안 같은 구의 신고 건수(구 활동량), 같은 센터의 출동 건수(센터 활동량) |
| 정체 지수 | 직전 1시간 구 평균 속도 ÷ 평소 속도(학습 기간 평균). 1보다 작으면 평소보다 막힘 |
| D+ / D− | 출동 거리를 입력에 넣은 설정 / 뺀 설정. 거리는 대원이 나중에 적었을 수 있어 둘 다 본다 |
| 검증 | 모델 설정(하이퍼파라미터)을 고르고 학습을 언제 멈출지 정하는 데 쓰는 데이터 |
| 보정 | 모델이 낸 점수를 실제 비율에 맞는 확률로 고치는 단계. "60%라고 하면 실제로 10번 중 6번 늦는다"가 되게 만든다 |
| 시험 | 모든 설계를 끝낸 뒤 마지막에 한 번만 성능을 재는 데이터 |
| Brier | 예측 확률과 실제(0/1)의 차이 제곱 평균. **낮을수록 좋다.** 주 지표 |
| 누출 | 신고 시점에 알 수 없는 정보(미래 정보)가 학습에 들어가는 것. 성능이 부풀려지므로 막는다 |

## 3부. 학습 데이터 분할과 학습 방법

### 3.1 결론

- **지금 분할은 일반적인 8:1:1(또는 7:1:2) 무작위 분할이 아니다.** 연도 단위로 시간 순서대로 나눴다.
- 비율은 **학습 : 검증 : 보정 : 시험 ≈ 47 : 15 : 19 : 19** (46.50 : 15.36 : 19.27 : 18.87)이다.
- 참고로 8:1:2는 합이 11이라 비율이 성립하지 않는다. 교수님이 말씀하신 것이 **8:1:1**인지 **7:1:2**인지 팀에서 다시 확인한다.
- 이 프로젝트는 일반 분할에 없는 **보정 구간**이 하나 더 필요하고, **시간 순서**를 지켜야 해서 이 비율이 나왔다(3.4절).
- 교수님 피드백("서로 다른 데이터로 섞어가며 학습")은 시간 순서를 지키면서 학습 기간을 바꿔 가며 여러 번 검증하는 **롤링 검증**으로 반영하자고 제안한다(3.5절). 평가 설계 변경이라 **팀 합의 후** 진행한다.

### 3.2 현재 분할 (안전센터 코호트, `발표자료/중간발표/표/기초통계_안전센터_분할별.csv`)

| 구간 | 연도 | 건수 | 비율(전체) | 용도 |
| --- | --- | --- | --- | --- |
| 학습 | 2019–2022 (4년) | 1,275,974 | 46.50% | 모델 학습 |
| 검증 | 2023 (1년) | 421,592 | 15.36% | 하이퍼파라미터 선택, 조기 종료 |
| 보정 | 2024 (1년) | 528,744 | 19.27% | 확률 보정, 개발 중 성능 평가 |
| 시험 | 2025 (1년) | 517,895 | 18.87% | 설계 동결 후 1회만 |
| 합계 | 7년 | 2,744,205 | 100% | |

- 2025 건수는 서버 Spark로 안전센터 행 수만 셌다(2026-10-31, 전체 코호트 518,030건 중 517,895건). 라벨·성능은 보지 않았다.
- 2025년은 안전센터 비율이 99.97%로 2024년(96.1%)보다 높다. 2024년 2월 기록 체계 변경 뒤 현장대응단 기록이 거의 없어졌기 때문이다.

### 3.3 학습을 어떻게 시켰나 (순서대로)

1. **표 만들기**: 출동 1건이 1행. 열은 기본 피처(센터, 구, 시간대, 요일, 월, 공휴일, 관외출동, D+일 때 거리)와 라벨(8분 초과 여부). 범주 목록(센터·구)과 결측 대체값은 학습 구간에서만 만든다.
2. **학습(2019–22)**: 모델마다 후보 설정을 여러 개 만들어 학습 구간으로 학습한다.
   - LR: 규제 강도 C를 6개 값으로 바꿔 가며 학습
   - LightGBM: 정해진 탐색 공간(잎 수, 학습률, 최소 표본 수 등 7개)에서 **무작위로 20개 조합**을 뽑아 학습(시드 42). 조합마다 트리를 최대 5,000개까지 늘리되, 검증 구간 log loss가 100번 연속 나아지지 않으면 멈춘다(**조기 종료**)
3. **선택(2023)**: 검증 구간 log loss가 가장 낮은 설정 하나를 고른다. 검증 데이터는 학습에 섞지 않는다.
4. **보정(2024)**: 고른 모델의 출력 점수를 2024년 실제 결과에 맞춰 확률로 바꾸는 보정기(isotonic)를 만든다. 보정 성능을 잴 때는 2024년을 7일 단위 블록으로 나눠 두 묶음으로 만들고, 한쪽으로 보정기를 만들어 다른 쪽에서 평가하는 것을 번갈아 한다(cross-fit). 같은 데이터로 보정하고 평가해 점수가 부풀려지는 것을 막기 위해서다.
5. **시험(2025)**: 모든 설계를 동결(`freeze-v1`)한 뒤 **한 번만** 평가한다. 아직 하지 않았다.
- 모든 모델을 D+와 D− 두 설정으로 각각 학습한다. 클래스 가중치는 쓰지 않는다(가중치를 쓰면 출력이 확률이 아니게 되므로 보정기로 확률을 만든다).
- 모델끼리 공정하게 비교하려고 같은 분할, 같은 시드, 같은 탐색 공간, 같은 시행 횟수를 쓴다.

### 3.4 왜 이 비율인가 (8:1:1이 아닌 이유)

| 이유 | 설명 |
| --- | --- |
| ① 보정 구간이 하나 더 필요하다 | 이 프로젝트는 화면에 **확률 숫자**를 보여 주므로, 모델 점수를 실제 비율에 맞추는 보정 단계가 있다. 보정을 검증 데이터(설정을 고를 때 이미 쓴 데이터)로 하면 결과가 낙관적으로 나와서 따로 1년을 뗐다. 일반적인 학습·검증·시험 3분할보다 칸이 하나 많아 학습 비율이 줄었다 |
| ② 시간 순서를 지켜야 한다 | 서비스는 과거로 학습한 모델로 앞으로 올 신고를 예측한다. 무작위로 섞으면 미래 기록으로 학습해 과거를 맞히는 셈이 되어 실제 사용 성능을 알 수 없다 |
| ③ 같은 시간대 기록끼리 정보를 공유한다 | 같은 날 같은 시간의 신고들은 비, 교통 정체, 신고 몰림을 함께 겪는다. 섞으면 같은 비 오는 시간의 기록이 학습과 시험에 동시에 들어가 점수가 부풀려진다(누출) |
| ④ 해마다 분포가 크게 바뀐다 | 8분 초과율이 20.7%(2019) → 50.5%(2022) → 42.6%(2023) → 48.2%(2024)로 움직였다. 섞으면 이 변화가 가려진다. 나눠 두었기 때문에 "학습 41% vs 2024년 48%" 차이를 발견하고 보정으로 바로잡을 수 있었다 |
| ⑤ 연 단위로 끊어야 계절이 고르게 들어간다 | 강수(여름 장마, 겨울 눈), 월별 초과율 차이가 있어서 각 구간이 1~12월을 모두 포함하도록 연 단위로 나눴다 |
| ⑥ 보정은 가장 최근 해로 | 2024년 2월에 기록 체계가 바뀌었다(현장대응단 기록 소멸, 안전센터 18곳 신설). 시험(2025)과 체계가 같은 가장 최근 해로 보정해야 확률이 맞는다 |
| ⑦ 학습량은 충분하다 | 비율은 47%여도 학습 구간이 **127만 건**이라, 비율이 작아서 학습이 부족한 상황이 아니다 |

### 3.4-2 변수를 더할 때마다 어떻게 평가하나

기상·활동량·정체 변수를 하나씩 더할 때마다 "얼마나 좋아졌는지"를 계산할 자리는 이미 분할에 정해 두었다. 핵심은 **모든 단계를 같은 데이터, 같은 행, 같은 절차로 평가해 G0와의 차이만 본다**는 것이다.

| 구간 | 단계마다 하는 일 | 이유 |
| --- | --- | --- |
| 학습 2019–22 | G0, G0+강수, +활동량, +교통 모델을 각각 학습 | 추가 변수만 다르고 나머지는 같게 |
| 검증 2023 | 단계마다 **같은 탐색 공간·같은 20회**로 설정을 고르고 조기 종료 | 어느 단계도 튜닝을 더 받지 않게(공정 비교) |
| 보정 2024 | 단계마다 보정기를 만들고 cross-fit으로 Brier·log loss 계산 → **G0 대비 ΔBrier·Δlog loss** | 개발 중 비교는 여기서 한다 |
| (같은 2024) | ΔBrier에 **날짜 블록 부트스트랩 95% 신뢰구간**을 붙인다. 같은 날의 기록은 같이 뽑는다 | 0.001 차이가 우연인지 판단. 구간이 0을 포함하면 "차이를 확인하지 못함"으로 보고 |
| 시험 2025 | 설계를 동결한 뒤 모든 단계를 **한 번에 한 번만** 평가 | 2024년은 개발 중에 여러 번 봤으므로, 처음 보는 데이터로 최종 확인 |

- **같은 행으로 비교한다**: 강수·정체 값이 없는 시간이 있어도 행을 빼지 않고 "결측" 표시(예: `cong_missing=1`, 정체 지수 1)를 붙인다. 단계마다 평가 행이 달라지면 차이가 변수 효과인지 행 차이인지 알 수 없기 때문이다.
- **추가 변수도 누출 없이**: 정체의 평소 속도는 학습 구간(2019–22)만으로 계산하고, 강수·정체는 신고 시각 이전에 확정된 값만 쓴다. 그래서 검증·보정·시험 구간 값을 학습에 미리 보지 않는다.
- **롤링 검증(3.5절)**으로 "학습 기간을 바꿔도 ΔBrier 방향이 같은가"를 함께 본다.
- 판단 기준: 주 지표는 Brier·log loss, ΔAUC 0.005 미만은 해석하지 않는다. 좋아짐이 작거나 없어도 그대로 보고한다.

### 3.5 교수님 피드백 반영안: 롤링(확장 윈도) 검증

시간 순서는 지키면서 학습 기간을 바꿔 가며 여러 번 학습·평가한다. 한 번 나눈 결과의 운에 기대지 않고 "서로 다른 데이터로 여러 번 학습"한다는 피드백의 취지를 살린다.

| 회차 | 학습 | 평가 |
| --- | --- | --- |
| 1 | 2019–2020 | 2021 |
| 2 | 2019–2021 | 2022 |
| 3 | 2019–2022 | 2023 (현재 설정) |
| 4 | 2019–2023 | 2024 |

- 회차별 Brier·log loss의 평균과 범위를 함께 보고한다. 2025 시험 구간은 여기에도 쓰지 않는다.
- 이미 해 둔 것: 학습 구간을 2021–22로 줄인 변형, 보정 구간을 2~12월로 바꾼 변형 → 보정 후 Brier 차이 ±0.001 수준. 중간발표에서는 "분할을 바꿔도 결과가 크게 흔들리지 않는지 일부 확인했다"는 근거로 쓸 수 있다.
- 선택: 무작위 8:1:1 분할과 시간순 분할을 한 번씩 돌려 점수 차이를 보여 주면, "왜 섞지 않았는지"를 숫자로 설명할 수 있다(기말 전).

### S11. 모델 구축 방안: Hill et al. 기반 설계 [M]
- **핵심 메시지**: "Hill et al.(2025)의 그래디언트 부스팅 방식을 서울 데이터와 8분 초과 확률 문제에 맞춰 가져왔다."
- 내용
  - 선행 연구: **Hill et al. (2025), BMC Medical Informatics and Decision Making 25:143**. 스톡홀름 구급 출동 100만 건 이상을 그래디언트 부스팅(GBM)으로 분석해 긴급도·기상·지리·자원 부하와 도착 시간의 관계를 본 연구
  - 가져온 것: ① 모델 계열 → GBM 계열인 **LightGBM(G0)**을 주 모델로, ② 변수 구성 → 시간·지리·기상·자원 부하를 우리 데이터로 만들 수 있는 범위에서(시간대·요일·구·센터 → 강수 → 구·센터 활동량) 단계적으로 넣는다
  - 다른 점: 우리는 도착 시간과의 관계 분석이 아니라 **개별 신고의 8분 초과 확률**을 예측하고 **확률이 맞는지(보정)**를 주 결과로 본다. 활동량의 공간 단위(구·센터)와 교통 정체의 추가 예측가치를 같은 조건에서 나눠 비교한다. 국가·데이터가 달라 수치는 비교하지 않는다
  - 모델 4개(G0와 비교 기준선)

    | 모델 | 입력 | 역할 |
    | --- | --- | --- |
    | 단순 기준 | 센터 × 시간대 과거 지연율 | 바닥선 |
    | B0 | 출동 거리만, 로지스틱 회귀 | 거리 하나의 힘 |
    | LR | 기본 피처, 로지스틱 회귀 | 전통적 통계 기준 |
    | **G0** | 기본 피처, LightGBM | 기준 모델 |

  - 기본 피처: 센터, 구, 시간대, 요일, 월, 공휴일, 관외출동, (D+) 출동 거리
- 주의: 서지 사항은 기획서(`docs/01_기획서_v15.md` 4절)에 적힌 그대로 쓴다. 추계학술대회 제안 논문을 모델 근거로 들지 않는다

### S12. 학습 데이터 분할과 학습 방법 [M]

- 자료: `그래프/2_일변량/2-3_연도별_8분초과율.png`(분할 음영 포함)
- 주의: 팀이 롤링 검증 도입에 합의하지 않았으면 "계획"으로만 말한다. "8:1:2로 나눴다"고 쓰지 않는다

### S13. 1차 결과 (예비) [M]
- **핵심 메시지**: "거리가 가장 강한 신호이고, 보정 후 예측 확률이 실제 초과율에 맞춰진다."

## 6부. 예상 질문과 답

| 질문 | 답 |
| --- | --- |
| 데이터를 왜 8:1:1로 섞어 나누지 않았나 | 확률을 맞추는 보정 구간이 하나 더 필요하고, 같은 시간의 기록이 날씨·교통·신고 몰림을 공유해서 섞으면 점수가 부풀려진다. 해마다 초과율도 20.7%~50.5%로 움직인다. 대신 기간을 바꿔 가며 여러 번 검증한다(롤링) |
| 학습 비율이 낮지 않나 | 비율은 47%지만 학습 건수가 127만 건이라 부족하지 않다 |
| 변수를 더했을 때 좋아졌는지는 어디서 재나 | 모든 단계를 같은 학습·검증·보정 구간과 같은 행으로 돌려 G0 대비 Brier 차이를 2024년에서 재고, 날짜 블록 부트스트랩 신뢰구간을 붙인다. 최종 확인은 설계를 동결한 뒤 2025년에서 한 번만 한다 |
| Hill et al.을 재현한 것인가 | 재현이 아니다. GBM 방식과 변수 구성을 가져왔고, 문제(8분 초과 확률·보정)와 데이터(서울)가 달라 수치는 비교하지 않는다 |
| 거리는 사후에 적은 값인데 써도 되나 | 그래서 거리를 넣은 설정(D+)과 뺀 설정(D−)을 모두 보고한다. 서비스에서는 도로 거리로 대신한다 |
| LightGBM이 LR보다 좋지 않은데 왜 쓰나 | 기본 정보만으로는 차이가 없었다. 활동량·교통·날씨처럼 상호작용이 있는 정보가 들어갔을 때 차이가 나는지를 기말에 같은 조건으로 비교한다 |
| 확률을 왜 보정하나 | 학습 기간 초과율이 41%, 2024년이 48%라 보정 전에는 실제보다 낮게 예측했다. 화면에 보여 줄 숫자가 실제 비율과 맞아야 한다 |
| 센터 활동량은 효과가 없는데 왜 넣나 | 일변량에서는 약했지만 다른 정보와 함께 넣었을 때 예측가치가 있는지 확인하는 것이 Q1이다. 결과가 작아도 그대로 보고한다 |
| 화면 숫자는 모델 결과인가 | 지금은 가상 값이다. 기말에 학습된 모델과 연동한다 |
| 실제 출동에 쓸 수 있나 | 연구용 참고 정보다. 실제 출동 지령에 쓰지 않고, 다른 센터가 출동했을 때의 결과는 기록으로 검증할 수 없다 |
| 2025년 결과는 | 시험 구간이라 설계를 동결한 뒤 한 번만 평가한다. 지금 결과는 2024년 보정 구간 기준이다 |
